# Review recovery

Use the installed launcher and existing review id. These commands preserve the existing review and validation gates.

- To dismiss a materially drifted closure, use `review.py --id <id> --deslop-done --reason "<why the findings are dismissed>"`. This records the caller's reason without changing the reviewer verdict or findings. It requires a completed closure on the exact clean branch, HEAD, and merge-base; all other review and validation gates remain in force.
- To replace an existing ladder with stricter review, use `review.py --id <id> --restart-mode deep --reason "<why>"` while the original repo/base/branch/head/merge-base still match and the worktree is clean; plain `--mode deep --cd <repo-root>` is not a restart.
- To replace mistaken literal text in a frozen brief before accepting any findings, use `review.py --id <id> --restart-brief (Get-Content -Raw "<brief.md>") --reason "<why the old brief is invalid>"`. This creates a fresh same-mode successor on the same clean branch, unchanged merge-base, and current descendant head. The original cycle and findings history remain stored; cleanup, review, and validation do not carry over.
- When an approved contract change invalidates accepted findings awaiting a fix or follow-up, use `review.py --id <id> --restart-brief (Get-Content -Raw "<new-brief.md>") --contract-conflict <dimension> --reason "<approved change and why the old contract is obsolete>"`. Stop or finish any active follow-up first. This also works after reporting that same conflict separately, or recording REPLAN for it. It records REPLAN once and creates a linked same-mode successor under the new brief, preserving the old brief, findings, decisions, and evidence. It requires the same clean branch, unchanged merge-base, and current descendant head; review, cleanup, and validation start afresh. Ordinary finding fixes still continue on the existing id.
- If an older launcher inferred findings from a changed HEAD despite a completed clean follow-up, inspect the stored output and interdiff first. At the resulting budget checkpoint (including recorded REPLAN), use `review.py --id <id> --decision clean --reason "<caller confirms mistaken inference, unchanged behavior/coverage, and relevant validation passed>"`. This is an explicit attestation: old records cannot distinguish inference from a deliberate caller decision. Recovery requires the latest stored clean follow-up, no later review or running reviewer, the same clean branch and merge-base, and a descendant changing only Python files under `tests/` or Markdown/reStructuredText under `docs/`. Actual findings, contract conflicts, and RESLICE cannot use this correction. The original decisions, accepted-head records, and convergence decisions remain stored; an appended correction records the reason, head pair, and stored-output digest. Only its mistaken entry stops counting toward convergence. Remaining review/cleanup/GitHub gates stay scheduled, and validation must be recorded for the current head. This is not a budget reset.
- On `head_changed_after_review`, inspect `reviewed_head..current_head`. If the changes only fix stale tests to match already-reviewed behavior, do not rerun review; run the affected tests and required validation, then proceed. Rerun only if production code or intended behavior changed.
- For a read-only id check, run `review.py --id <id> --show-status`.
- If the caller session was restarted after reviewer output was produced, run `review.py --id <id> --show-findings` to recover stored reviewer text without launching another review.
